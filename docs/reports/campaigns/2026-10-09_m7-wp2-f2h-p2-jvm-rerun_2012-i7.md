## Context & terms

- **R-007:** the tracked risk that a storage fault weakens the brute-force lockout of the app (FR-174). Change F2 left
  four residuals:
  - **R-007/1:** a failed read at startup leaves the lockout manager empty, so a stored lockout is not enforced.
  - **R-007/2:** the degraded lock of a failed write lives in memory only and ends with the process.
  - **R-007/3:** a process death before an admitted change reaches storage loses that change.
  - **R-007/4:** a failed reset leaves the old count and deadline in storage, and a restart brings them back.
- **Phase P2:** the R-007 test plan (`2026-09-23_R007_F2_HARDENING_TEST_PLAN.md`) first characterizes the current
  app, before any fix. Its case IDs are H01 to H06 (healthy storage), R1.1 to R4.4 (one group for each residual), and
  X cases (cross-cutting). Phase P3 then compares candidate fixes.
- **Harness:** the JVM harness in `security/harness` runs the production `LockoutManager` in simulated processes over
  a simulated store. The store keeps the durable state apart from the cache of each process. A kill fences the dead
  process, so that it cannot change the store. A reference model checks each step.
- **Fixtures and clocks:** `D=(count, wall deadline)` is the stored pair, and `Z=(0,0)` is the empty pair. The wall
  clock starts at W0 = 1,000,000 ms, and the elapsed clock at E0 = 5,000,000 ms. The fifth failure locks for T = 30 s,
  each later failure doubles the window, and the cap is 30 min.
- **Degraded lock:** after a failed write, the manager blocks further attempts from memory for a lock window. The state
  reads `degraded=true` while storage does not hold that lock.
- **Verifier entry (V):** one PIN that reached verification. The `GatedCaller` class reads the lockout state before
  each attempt and verifies a PIN only while the state is Available, as the live callers do.
- **Two verdicts:** "As predicted" says whether the baseline matches the prediction of the test plan. "Objective met"
  says whether the security objective of the case holds. A test that correctly reproduces a residual is "as
  predicted: yes" and "objective met: no".
- **Evidence file:** each test writes one file with its verdict, the source identity (the `# source_` header lines),
  the recorded values, and the ledger trace of each harness.

## Notes and limits

- **Simulated storage and process death.** The runs used no Android preferences, no keystore, and no real process
  death. The harness fence stands for a death. The simulated store commits in one step, so a death inside the
  platform commit is a device case.
- **Virtual time.** The harness moves both clocks by hand, so each time value is exact. The values are not device
  timings.
- **Stand-in caller.** The `GatedCaller` class follows the rule of the live callers, but it is not their code.
- **Injected faults.** The faults show the behaviour under a fault. They do not estimate how often a fault happens.
- **No timing measurement.** This lane measured no latency or responsiveness. The P2 device decisions moved those
  distributions to the start of P3.
