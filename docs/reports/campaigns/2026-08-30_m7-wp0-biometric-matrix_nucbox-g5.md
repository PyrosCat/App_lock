## Context & terms (so this report stands alone)
- **BAL (background-activity-launch).** Android blocks an app from starting an `Activity` while it is in the *background* (restricted from Android 10 / API 29, tightened in 14/15). An app can be *exempted* — among other ways — by **holding the `SYSTEM_ALERT_WINDOW` (overlay) permission** (a standing exception on every version tested here), or by **owning a visible window**. These are independent exceptions: either one qualifies.
- **biometric-via-BAL (ADR-020 case (a))** — the path under test. `BiometricPrompt` cannot live in a non-Activity window, so the app-lock hosts it in a transparent `Activity` (**`SpikeBiometricActivity`**). While a protected app is foreground, App Lock is in the background with only its **overlay** window visible; it launches the transparent host as a **background launch permitted by that visible overlay**.
- **the spike** — the throwaway WP0 prototype (`platform/spike/`): a usage-poll foreground service + the overlay + `SpikeBiometricActivity`, all drivable over `adb`. Deleted at WP0 close; the durable output is this evidence + ADR-020/021.
- **Item A (mandatory)** — does the biometric host **launch** from the background (BAL permitted)? Needs *no* fingerprint hardware: an `ERROR 11` "no fingerprints enrolled" callback still proves the host launched and the prompt path ran.
- **Item B (optional/confirmatory)** — does a **real fingerprint match** authenticate? Needs a `google_apis` image (which ships the fingerprint HAL) and an enrolled print.
- **Acronyms.** **FGS** = foreground service. **SAW** = `SYSTEM_ALERT_WINDOW` (the overlay permission). **HAL** = hardware abstraction layer (here, the fingerprint sensor driver). **ADR-020** = the overlay/biometric decision; **ADR-021** = the poll/detection decision. **a11y** = accessibility.

## Headline
- **Item A (BAL launch, api30/33/36): PASS on all three.** The transparent biometric host launches from the background on every level, with **no BAL denial** anywhere. This **closes ADR-020's "biometric-via-BAL proven on API 30/33/35/36" residual** (Moto G already did API 35 on real hardware).
- **Item B (real match, google_apis api33): PASS.** A simulated fingerprint match authenticated (`M7Spike: biometric SUCCESS`), confirming the full overlay→BAL→prompt→match path on an emulator.

## Item A — BAL launch + prompt (api30/33/36) — PASS (all three)
Per lane: foreground App Lock (so the FGS start is allowed on API 31+) → start the poll FGS with `target=deskclock` → bring the protected app forward (App Lock is now background, only its overlay visible) → fire `com.applock.spike.BIOMETRIC` → the host launches via BAL and `BiometricPrompt.authenticate()` runs. **Pass = a `M7Spike: biometric …` line + no BAL denial in `ActivityTaskManager`.**

The app holds `SYSTEM_ALERT_WINDOW`, which is a **standing BAL exception on every Android version** (Android's BAL-exceptions doc lists *both* a held SAW permission *and* a visible window as independent exceptions), so the biometric-host launch is permitted on all three lanes via that exception alone; a visible overlay, when present, is simply a second valid basis. The per-lane log lines below just name **which** qualifying reason the OS happened to report — they do **not** indicate a version-dependent requirement.

| Lane (Android) | Overlay present at launch | Reason string logged by `ActivityTaskManager` | Launch / `BiometricPrompt` |
|---|---|---|---|
| **api36** (16) | ✅ up (`mAlertWindows={…AppLockSpikeOverlay} mPackageName=com.applock`) | **`BAL_ALLOW_NON_APP_VISIBLE_WINDOW`** — the visible-overlay route fired here (the app also holds SAW) | `START SpikeBiometricActivity` (fresh ts), no denial → `ERROR 11` |
| **api33** (13) | ✅ up + focused (`mCurrentFocus=AppLockSpikeOverlay`) | **none** (Android 13 logs no reason) — route undetermined; both held-SAW and the visible overlay were available | `START …` (fresh ts), no denial → `ERROR 11` |
| **api30** (11) | drew late that one run (fresh-install artifact — see note) | **"allowed because SYSTEM_ALERT_WINDOW permission is granted"** — the held-SAW route fired here | `START …` (fresh ts), no denial → `ERROR 11` |

- On every lane the host (`SpikeBiometricActivity`) launched (a `START …SpikeBiometricActivity` line from `ActivityTaskManager` at each fire, with a fresh timestamp — not a stale callback), `BiometricPrompt` ran, returned `ERROR 11` (no enrolled print — expected on a bare emulator), and there was **no background-activity-launch denial**. That is an Item-A PASS per lane.
- **Finding — the launch is carried by the held SAW permission on all three lanes; the visible-overlay route additionally applies where the overlay is up.** `BAL_ALLOW_NON_APP_VISIBLE_WINDOW` (api36) and the SAW reason (api30) are just the two different qualifying reasons the OS logged; api33 logged neither, so its route is undetermined. This is *not* an evolution of the requirement by version — held-SAW qualifies throughout. (The Android-15 narrowing that *does* require an actually-visible overlay governs **starting a foreground service** from the background — a separate rule, ADR-021 — not this activity BAL, ADR-020.)
- **api30 note (corrected — steady-state reliable, but a robust fresh-install DETECTION failure; NOT dexopt).** The ~18 s draw happened right after the spike was (re)installed. Measured: **(1)** warm steady-state is reliable — 21/21 trials (18 earlier warm+cold-reboot + a 3-trial warm control) detected in 0.5–2.5 s, **0 misses**; but **(2)** reinstall → immediate trial **missed 9 of 10** (n=10), and **every one of the 9 misses logged no `LOCK` at all** — the poll's `queryEvents` never *detected* the foreground app (it is **not** an overlay-draw failure; the lone success detected in 0.6 s). So the outlier is **robustly reproducible (~90 %)** and tied to the fresh install, not a steady-state property — which refines my earlier "not flaky at all" (those clean trials were all warm). It is **NOT dexopt** (the controlled reinstall trials logged **0 `dex2oat` lines** — my earlier dexopt attribution was wrong) and **NOT appops-revocation** (`get_usage_stats` stayed `allow`). Best current read: **`UsageStats`/`queryEvents` does not report foreground events for a just-(re)installed package for a window after install** — but the exact cause is **not isolated**, and I did not test whether a *single* fresh install (vs this repeated-reinstall harness) or the appops-grant timing behaves the same. Relevance: it does **not** gate the biometric BAL (held SAW carries the launch regardless of a drawn overlay); but since it's a *detection* gap right after install/grant, **WP3 should confirm the production `UsageAccessDetector` detects reliably in the first seconds after setup** (the R-005 `loading`-until-first-snapshot readiness model likely covers this — worth verifying against this behaviour).

## Item B — real fingerprint match (google_apis api33) — PASS (optional/confirmatory)
- Set a device credential (`locksettings set-pin 1234`), then enrolled a fingerprint through the Settings flow (`FingerprintEnrollIntroduction` → "I AGREE" → ~12 simulated `adb emu finger touch` cycles → "Fingerprint added"; `dumpsys fingerprint` = 1 enrolled print).
- Ran the Item-A sequence; with `mCurrentFocus=BiometricPrompt` (prompt launched via BAL over the overlay), a matching `adb emu finger touch 1` produced **`M7Spike: biometric SUCCESS`**.
- Confirms the full **overlay → BAL → `BiometricPrompt` → match** path on an emulator, complementing the Moto G real Class-3 match on API 35.

## Disposition
- **ADR-020:** this closes the last platform-evidence residual — the transparent-Activity biometric host launches from the background on **API 30/33/36 (emulator) + 35 (Moto G real)**, via a qualifying BAL exception on each and with no denial. Note on the mechanism: the specific visible-overlay route of ADR-020 *case (a)* is explicitly confirmed on api36 (`BAL_ALLOW_NON_APP_VISIBLE_WINDOW`) and the overlay was present on api33; on api30 the launch is carried by the held SAW permission (the overlay was not up at the fire) — so the path is proven on all three, even more robustly than case (a) alone requires. With ADR-021's poll interval and the NFR-PERF-012 figure ratified, the lead can move **ADR-020 / ADR-021 Proposed → Accepted**. No ADR body edited here.
- **FR-027:** the biometric affordance is evidenced; the RTM promotion happens at **WP6** with the full matrix, not here — **WP0 lands no production code** (M7_PLAN §6).
- **PIN fallback is always present**, so biometric is never a hard dependency; Item A is about the BAL *launch*, not the sensor.

## Follow-ups
1. **api30 first-detection-after-install fails ~90% (n=10) — WP3 to verify post-setup detection.** Steady-state is reliable (21/21 clean, 0.5–2.5 s), but reinstall → immediate trial **missed 9 of 10**, every miss with **no `LOCK` logged** (the poll's `queryEvents` never detected the foreground app — not a draw failure). **Not dexopt** (0 `dex2oat`), **not appops** (stayed granted); the mechanism (`UsageStats` not reporting events for a just-(re)installed package) isn't isolated, and single-fresh-install vs repeated-reinstall wasn't separated. Since it is a *detection* gap right after install/grant, **WP3 should confirm the production `UsageAccessDetector` detects reliably in the first seconds after setup** — the R-005 `loading`-until-first-snapshot readiness model likely holds correctly through it, but verify against this behaviour.
2. Item B was run on one `google_apis` lane (api33) as confirmation; the authoritative real-hardware match remains the Moto G (API 35). Additional `google_apis` lanes are optional.
