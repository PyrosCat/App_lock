| Metric | Result | Budget (§11) |
|---|---|---|
| ABSENT | **0** | 0 (hard) |

The overlay wins the rapid-relaunch race on every burst. Screenshot-confirmed the overlay fully covers

device already clean on the old engine — this does NOT close R-002; the emulator A/B does).

### End-to-end latency + poll-interval sweep (D1) — n=100 each, portrait, API 35
Measured via the spike's overlay first-frame timestamp (`OverlayController.logFirstDraw`), 100 controlled
transitions per interval, rotation locked portrait:

| Poll interval P | p50 | p95 | p99 | max | mean | min |
|---|---|---|---|---|---|---|
| 400 ms | 87 | **456** | 471 | 481 | 158 | 64 |
| 300 ms | 187 | **329** | 350 | 358 | 193 | 66 |
| 200 ms | 163 | **226** | 229 | 229 | 157 | 66 |
| 100 ms | 85 | **136** | 147 | 148 | 91 | 55 |

Units ms. **p95 ≈ P + ~40 ms** — the tail tracks the poll interval almost exactly, so P is the p95 dial
(halving P halves the worst case). No floor is hit down to 100 ms; the only floor is the best case
(min ~55–66 ms = `queryEvents` recording + overlay draw). **200 ms is the largest interval that keeps
end-to-end p95 < 250 ms** (226 ms). This is the **D1** *latency* half only — battery (wakeups /
`queryEvents` scale inversely with P; 100 ms = 4× the 400 ms rate) is the counterweight and needs the
battery **soak** before P is fixed; if a tight tail and low drain both matter, that is the argument for
the adaptive/event-triggered polling ADR-021 rejected. The chosen P lands in ADR-021's SSOT (detector
interval constant + NFR-PERF-012), not the ADR body (GOVERNANCE §2.7). Real-device arm64 on **API 35**;
API-36 = NucBox lane.

**Method note (measurement fix, not a device issue):** under rapid app-switching the default logcat
buffer rotates the `M7Spike` lines out, which made `logcat -d | grep -c` plateau at ~10 and *look* like
a detection stall. It was not — detection/draw ran throughout (LOCK:E2E 1:1, samples present late in the
run). Capturing the full n=100 required `adb logcat -G 16M`. The cache/cadence theories were tested
(slow cadence + cursor-reset batches) and did **not** change the count, confirming the artifact.

### Biometric-via-BAL — PASS (ADR-020 case (a))
With the overlay up over a protected app, triggering the biometric host: the transparent
`SpikeBiometricActivity` **launched from the overlay** (Task `visible=true, translucent=true` — a
background-activity-launch permitted by the app's visible overlay window), the system `BiometricPrompt`
rendered and held focus (`mCurrentFocus=BiometricPrompt`), a real fingerprint **authenticated**
(`M7Spike: biometric SUCCESS`), and the host `finish()`ed cleanly with focus returning to the overlay.
Confirms the ADR-020 biometric path on real hardware (Moto G side-mounted sensor, API 35). The prompt is
a `FLAG_SECURE` system window, so it does not screencap. (The spike logs SUCCESS only; wiring
success → overlay-dismiss/unlock is WP2, not the spike.)

### Poll gating
Confirmed the poll pauses while the device is asleep/locked (`queryEvents` returns nothing) — observed
directly when the phone slept mid-test — matching the §2.4 contract.

## Platform finding — overlay hidden over Settings (INTENTIONAL, documented)
Android **force-hides** `TYPE_APPLICATION_OVERLAY` windows over Settings / permission / sensitive
screens (`mForceHideNonSystemOverlayWindow=true`, `shown=false`). This is the documented
anti-tapjacking feature `setHideOverlayWindows()` / `HIDE_OVERLAY_WINDOWS` (Android 12+; some OEMs
earlier), **not a defect**. Consequence: an overlay-based lock **cannot cover the Settings app** — a
real product gap vs the accessibility approach. **For the lead:** candidate ADR-013B implementation
note / new ADR (§2.2 discovered-constraint) and a `RISK_REGISTER.md` entry (§5.2).

## Method notes (test fixes made to get a valid result)
- **OV-4 target must be a normal app** — `com.android.settings` is overlay-hidden (above), so the test
  target is `com.google.android.deskclock`, launcher component resolved at runtime.
- **Focus read from `dumpsys window`**, not `dumpsys window windows` — on Android 15 `mCurrentFocus` is
  absent from the latter (version-dependent `dumpsys` format; the WP1 "revalidate the grep per lane"
  caveat). Not a coding bug.
