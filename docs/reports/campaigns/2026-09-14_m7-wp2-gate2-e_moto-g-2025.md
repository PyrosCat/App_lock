## Notes

- **A first-run defect was found and fixed (traceability).** The first run, on `4c9f311` as committed, crashed
  the app process on the first test with `IllegalStateException: ViewTreeLifecycleOwner not found from
  ...OverlayLockPresenter$OverlayRoot`, thrown from `AbstractComposeView.onAttachedToWindow`, which aborted the
  whole run (1/18). The cause was that `OverlayLockPresenter` set the three ViewTree owners (lifecycle,
  viewmodel, and savedstate) on the child `ComposeView`, whereas Compose resolves the window recomposer from the
  **window-root** view (`OverlayRoot`, the view handed to `WindowManager`) and calls `findViewTreeLifecycleOwner()`
  there, so owners on a child are not found and composition creation throws on attach. The fix sets the owners on
  `OverlayRoot` before `addView`. This is a universal defect that would crash on any real device, and the JVM
  suite cannot attach a real window, so Gate-2 is what surfaced it. The 17/18 result above is the re-run after
  the fix, and the JVM gate was re-confirmed post-fix at 297 tests, 0 failures, and detekt clean. Committed
  `4c9f311` still carries this crash until the follow-up fix commit lands, though production is unaffected until
  F wires the overlay in, because there is no DI cutover yet.
- **FLAG_SECURE is verified in three parts, and only one of them runs here.** This debuggable APK drops
  FLAG_SECURE by design so the content assertions can read the overlay; the pure flag policy is JVM-tested
  (`OverlayWindowFlagsTest`); and the deployed-secure proof is a separate non-debug screencap (Open item 2).
- **No accessibility grant is needed.** The suites drive the `LockPresenter` directly, so they are insulated from
  the Moto G Restricted-Settings accessibility flakiness (R-001a); adb reachability plus the overlay app-op was
  all that was required. The phone was set to stay awake while charging (`svc power stayon true`) for the run,
  and that is reversible with `... false`.
- **State hygiene was only partial for the full command.** The two change-E suites snapshot the overlay app-op
  **before** the overlay assumption and restore it (and `OverlayLockPresenterUiTest` also restores the biometric
  setting), so even a skipped E-suite run restores the state. The full `connectedProdDebugAndroidTest`, however,
  also runs `OverlayRaceUiTest`, which sets `com.applock` `android:get_usage_stats` and `android:system_alert_window`
  to `allow` and did not restore them, so this run left those two app-ops granted on the device. Clean up this
  run's residual (or restore your prior values) with:

  ```
  adb shell appops set com.applock android:get_usage_stats default
  adb shell appops set com.applock android:system_alert_window default
  ```

  This is fixed in the follow-up: `OverlayRaceUiTest` now snapshots both app-ops before forcing them to `allow`
  and restores them (Known-only) in `@After`, so a future connected run leaves the grant state untouched.

4. A **successful biometric unlock from the overlay** is authored but pending an opt-in emulator lane, because

   method `BIOMETRIC`. A real fingerprint cannot be injected from instrumentation, so the test is gated on
   `-e inject_biometric_success 1` plus an enrolled authenticator, and the fleet harness injects the finger
   (`adb emu finger touch`) when it sees the `AppLockBiometricReady` logcat marker. A manual fingerprint-success

   AOSP emulator).
