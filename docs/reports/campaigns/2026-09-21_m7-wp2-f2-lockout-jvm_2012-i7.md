## Context & terms

- **FR-174** — Authentication Brute Force Protection (SecurityRequirements, Critical). Enforced by
  `LockoutManager`: failures below the 5-failure threshold are counted; from the threshold on, each failure starts
  a doubling lockout window (30 s base, 30 min cap); a success resets.
- **R-007** — the risk that a degraded encrypted store silently drops the lockout counter, so a lockout is never
  enforced. F2 makes a storage-write failure a first-class, fail-secure outcome (an in-memory authoritative
  snapshot plus a degraded in-memory fallback that still blocks the next attempt).
- **F2** — M7 WP2 change F2, the R-007 rework of `LockoutManager`, its storage adapter, the legacy
  `ApplicationLockEngine`, and the `LockEngineRuntime` lockout boundary. See the risk register R-007 entry and the
  changelog F2 entry for the full design.
- **The gate** — the local build/test command the project runs before a code change is considered complete; the
  same unit-test task (`testProdDebugUnitTest`) also runs per push in CI (`.github/workflows/ci.yml`), with the
  reports uploaded as the tests+lint artifact (short retention). This report is the curated, durable conclusion of
  the local run, not a dump of that CI output.

`LockoutManagerTest` is the direct FR-174 regression suite. It covers the lockout math (threshold, doubling, cap,
expiry, counter-survives-restart), the R-007 degraded fallback (a failed below-threshold write and a failed
threshold write both arm an in-memory deadline; a `commit() == false` is treated exactly like a throw), the
per-operation completion rules (each attempt reports its own count and durability; stale/older completions are
fenced), the cold-start re-seed (a failed seed read degrades to Available then recovers off-main, and is disabled
after the first local mutation), the reset persistence outcome (a committed reset resolves committed; a
`commit() == false` or a throwing reset resolves not-committed but still clears in memory without re-locking), and
the lifecycle (an in-flight write during shutdown publishes nothing).

`LockEngineRuntimeTest` covers the interpreter that drives `LockoutManager` on the overlay/runtime path (inert in
production until F6, exercised by these tests): the degraded-lockout projection, the self-gate awaited path, the
newly observable failed-reset diagnostic (`lockout_reset`), and the drain-liveness regression that proves a stalled
failure write does not freeze the single drain (five failures admit and enforce immediately, a queued screen-off is
processed, and each off-drain completion keeps its own count and target once persistence is released).
