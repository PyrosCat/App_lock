Analysis — R-002 rapid-relaunch lock race: root cause   (2026-08-09)
-------------------------------------------------------------------
Root-cause analysis of R-002 (HF-002), backed by code + the NucBox WP2
logcat evidence + external research.

- docs/reports/security/2026-08-09_r-002-rapid-relaunch-race-analysis.md —
  NEW (first report under reports/security/). R-002 is a STRUCTURAL race, not
  a tunable flake: the engine detects reactively via an async accessibility
  event, then covers the app with a full-screen noHistory Activity that
  competes in the same task ordering as the app's own am-starts and
  self-finishes the instant it loses. Detection isn't the miss (engine fires
  5-8 lock launches/burst); the lock just can't win the last window
  transition. BAL restrictions (API 29+) add platform headwind and explain
  the noisy, non-monotonic per-API rate.
- Fix is a MECHANISM change, not tuning: suspend the target app (Device
  Owner) so it can't foreground pre-auth (what robust lockers do); or hold a
  persistent overlay instead of a raced noHistory activity; at minimum drop
  noHistory so a lost race self-heals. Complements ADR-013A/R-001 (detection
  half) — accessibility-reactive covering shouldn't be the sole enforcement.
- No code/RTM change. R-002 itself lives in RISK_REGISTER (lead-owned); this
  analysis record is written for that risk to reference. A timestamped
  activity-ordering trace on real hardware is the recommended confirmation.

Security — R-002 filed: lock-engine rapid-relaunch race (NucBox WP2 matrix)   (2026-08-06)
---------------------------------------------------------------------------
Follow-up on the NucBox WP2 emulator-matrix report (2039693,
docs/reports/campaigns/2026-07-23_wp2-matrix_nucbox-g5.md). Docs-only.

- NucBox matrix run (API 26/29/33/35) found the F4 rapid-relaunch defense (OV-4)
  fails intermittently on EVERY emulator level — 12-37% in focused loops, NOT
  graded by API. Root cause is a window-ordering race, NOT a detection gap: the
  engine fires a lock decision on every relaunch, but the rapidly-relaunched
  protected-app window outruns the noHistory LockScreenActivity (self-finishes),
  leaving the protected app foreground with no lock for the 6-12s poll window.
  This is the exact race the Phase-3 mitigation anticipated (ApplicationLockEngine
  .kt:61) and tried to counter (re-launch NEW_TASK|CLEAR_TOP, :123) — the
  mitigation is probabilistic, not deterministic. So HF-002 (fast-relaunch
  bypass) was NOT fully closed in Phase 3.
- Filed RISK_REGISTER R-002 (Severity High, pending real-hardware; Status Open).
  Real-hardware severity unresolved: Moto G 2025 (fast arm64) was clean; a
  slower/older real device is untested = the decisive open question. Rated High
  precautionarily (enforcement bypass).
- Fix direction ties to M2: the noHistory *Activity* loses the window race by
  construction; the two-tier baseline **overlay** presentation (AS-020,
  SYSTEM_ALERT_WINDOW) sits on top and should resist it — so the open
  overlay-vs-activity-launch decision (ADR-013A) must weigh R-002.
- Also noted in R-002: the run_all -n 2 gate under-samples this probabilistic
  race (API 29 + 33 passed -n 2 yet focused loops found real bypasses) — WP2/WP8
  harness should raise OV-4 burst count.
- DEFERRED (not done here): citing R-002 from the TM (THR-ENF-004, HF-002

- RTM (§1): requirements are living artifacts. Closed status vocabulary
  with exact definitions — adds `in-progress` and `invalidated` (a change

  edit; ff-only when behind; STOP + escalate on divergence; force-push and
  history rewrites prohibited; user performs all commits/pushes (D4);
  per-file-class merge-conflict rules (reports keep both; changelog keeps
  both entries; rtm.csv evidence wins; source logic → escalate); hand-off
  rule: work moves between machines only as pushed commits.
- Dates (§4): absolute ISO dates only, taken from the system clock at
  writing time; filing vs capture date distinction; no back/future-dating.
- RTM.md, adr/README.md, docs/README.md updated to defer to GOVERNANCE.md.

Phase 3 — Encrypted vault + intruder selfie   (2026-07-15, uncommitted)
----------------------------------------------------------------------
Encrypted media vault and intruder-selfie capture, plus two security
fixes found during validation.

Added:
- Encrypted vault (vault/ package). SAF import copies each file into an
  AES-256-GCM EncryptedFile blob (UUID-named, perms 0600) under filesDir;
  the human-readable index (name/type/size/date) lives only in the
  SQLCipher DB. Supports in-memory image preview, byte-identical export
  round-trip, secure delete (index row + ciphertext blob), and an opt-in
  "delete originals from device" prompt after import (FR-106..119).
- Intruder selfie (privacy/ package). After a configurable number of
  consecutive failed unlocks, captures a front-camera photo with no
  visible camera UI (CameraX ImageCapture bound to a throwaway
  LifecycleOwner) and writes the JPEG straight into an EncryptedFile.
  Logs an event with timestamp/app/method/attempts/battery/orientation,
  raises a high-priority owner notification, and exposes a history viewer
  (FR-081/082/084/085). Threshold is user-configurable (3/5/10).
- Shared EncryptedFileStore helper (androidx.security.crypto) backing both
  vault blobs and intruder photos.
- Database v2: new intruder_events and vault_items tables via a
  hand-written MIGRATION_1_2.
- Settings: intruder-selfie toggle (requests CAMERA at opt-in) and
  failed-attempt threshold; CAMERA permission + camera uses-feature.

Fixed (security defects found during validation):
- Self-gate was not re-applied on resume: after unlocking once,
  backgrounding and resuming the app returned straight to the app list,
  leaving the vault and intruder log reachable with no re-authentication
  (violated FR-108). Now re-gates on ON_STOP via a SelfLock lifecycle
  observer, skipping config changes and carving out the SAF picker
  round-trip so import/export doesn't bounce the user to the gate.
- Fast-relaunch gating bypass: rapidly relaunching a protected app slid
  its window over the lock screen (which self-finishes via noHistory),
  and the engine deduped the repeat foreground event, so it never
  re-locked and the app's content was exposed. Removed the same-package
  dedup; a protected app with no session now re-locks on every foreground
  event (idempotent singleTop launch, only the first transition logged).

Validation:
- 67/67 JVM unit tests; clean debug and release (R8) builds.
- On-device E2E on headless Pixel_5 (API 30): gating (back / recents /
  fast-switch / rapid-relaunch), vault encrypt-export-delete, reboot
  persistence (data + lockout counter FR-174 + watchdog + a11y rebind),
  force-stop, incoming-call interruption, low-battery capture, encryption-
  at-rest sweep, and clean-room fresh install (encrypted-from-birth DB, no
