Security — R-002 filed: lock-engine rapid-relaunch race (NucBox WP2 matrix)   (2026-08-06)
---------------------------------------------------------------------------
Follow-up on the NucBox WP2 emulator-matrix report (2039693,
docs/reports/campaigns/2026-07-23_wp2-matrix_nucbox-g5.md). Docs-only.

- NucBox matrix run (API 26/29/33/35) found the F4 rapid-relaunch defense (OV-4)
  fails intermittently on EVERY emulator level — 12-37% in focused loops, NOT
  graded by API. Root cause is a window-ordering race, NOT a detection gap: the
  engine fires a lock decision on every relaunch, but the rapidly-relaunched
  protected-app window outruns the noHistory LockScreenActivity (self-finishes),
  leaving the protected app foreground with no lock for the 6-12s poll window.
  This is the exact race the Phase-3 mitigation anticipated (ApplicationLockEngine
  .kt:61) and tried to counter (re-launch NEW_TASK|CLEAR_TOP, :123) — the
  mitigation is probabilistic, not deterministic. So HF-002 (fast-relaunch
  bypass) was NOT fully closed in Phase 3.
- Filed RISK_REGISTER R-002 (Severity High, pending real-hardware; Status Open).
  Real-hardware severity unresolved: Moto G 2025 (fast arm64) was clean; a
  slower/older real device is untested = the decisive open question. Rated High
  precautionarily (enforcement bypass).
- Fix direction ties to M2: the noHistory *Activity* loses the window race by
  construction; the two-tier baseline **overlay** presentation (AS-020,
  SYSTEM_ALERT_WINDOW) sits on top and should resist it — so the open
  overlay-vs-activity-launch decision (ADR-013A) must weigh R-002.
- Also noted in R-002: the run_all -n 2 gate under-samples this probabilistic
  race (API 29 + 33 passed -n 2 yet focused loops found real bypasses) — WP2/WP8
  harness should raise OV-4 burst count.
- DEFERRED (not done here): citing R-002 from the TM (THR-ENF-004, HF-002
  annotate-incomplete, §12.41) — a next-TM-revision touch, flagged to user.

Governance — ADR supersession numbering: suffix-lineage convention   (2026-08-04)
---------------------------------------------------------------------------
User-approved change to GOVERNANCE.md §2 (approval 2026-08-04): a superseding
ADR is now numbered by lineage suffix rather than the next integer.

- A 1-to-1 supersession takes the superseded ADR's lineage-root number + the
  next unused letter (ADR-013 -> ADR-013A -> ADR-013B). A multi-parent
  supersession and any new independent decision keep the next integer.
  Lettered-suffix IDs are permanent and non-reusable like integers.
- GOVERNANCE §2.3/§2.4 updated; docs/README naming convention (rule 2) updated;
  the ADR index lists a superseding ADR directly beneath its lineage root.
- First application: the two-tier-detection ADR (drafted in-session as ADR-016)
  is renamed to ADR-013A before commit; integer 016 stays free (M1_PLAN D2
  Konsist earmark unchanged).
- Rationale: make supersession lineage visible in the identifier; Status and
  Supersedes/Superseded-by links already carried the distinction.

  (FR-081/082/084/085). Threshold is user-configurable (3/5/10).

  vault blobs and intruder photos.
- Database v2: new intruder_events and vault_items tables via a
  hand-written MIGRATION_1_2.
- Settings: intruder-selfie toggle (requests CAMERA at opt-in) and
  failed-attempt threshold; CAMERA permission + camera uses-feature.

- Self-gate was not re-applied on resume: after unlocking once,
  backgrounding and resuming the app returned straight to the app list,
  leaving the vault and intruder log reachable with no re-authentication
  (violated FR-108). Now re-gates on ON_STOP via a SelfLock lifecycle
  observer, skipping config changes and carving out the SAF picker
  round-trip so import/export doesn't bounce the user to the gate.
- Fast-relaunch gating bypass: rapidly relaunching a protected app slid
  its window over the lock screen (which self-finishes via noHistory),
  and the engine deduped the repeat foreground event, so it never
  re-locked and the app's content was exposed. Removed the same-package
  dedup; a protected app with no session now re-locks on every foreground
  event (idempotent singleTop launch, only the first transition logged).
